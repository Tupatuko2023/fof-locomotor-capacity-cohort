# v0.1.0 release runbook

**Status: COMPLETED / HISTORICAL. Do not rerun this procedure for `v0.1.0`.**

The GitHub software release was published on 2026-08-15. The annotated
`v0.1.0` tag resolves to commit
`63f00831c0c9cc5a8d7fad1c705922d1afe084af`; the published curated ZIP has
SHA-256 `9b70b06d6e7dd729a73f6fa20667f6610fbd4c029aa551ba3f0282b70c6fec81`.
No Production Zenodo record or DOI was created by this procedure.

## Purpose and boundary

This runbook records the completed preparation and publication procedure for
the independent, synthetic-only `v0.1.0` research-software release. It did not
publish a manuscript, supplement, scientific results, participant data,
Production Zenodo record, or DOI. Zenodo Sandbox draft `587120` is unpublished
validation evidence only; it is not a release artifact or citation target.

Commands below are retained as historical release evidence. They are not
instructions to recreate, move, replace, or republish `v0.1.0`. Recording a
completed gate did not authorize a later gate, and this record grants no new
release, tag, asset, Zenodo, DOI, or publication authority.

## Hard-stop conditions

Abort the release procedure immediately if any of the following occurs:

- a validation or render command fails;
- the worktree is dirty, contains unexpected tracked changes, or differs from
  the explicitly selected release commit;
- local and remote state are not synchronized, or the selected SHA drifts;
- the curated-bundle build, manifest, checksum, privacy, secret, or archive
  boundary check fails;
- local development or governance material, protected data, protected results,
  or an unexpected path appears in the release tree or curated bundle;
- `v0.1.0` already exists locally or remotely;
- any requested action crosses the software-release boundary defined above.

Do not repair a failed release by moving or force-updating a tag. Stop, preserve
the evidence, and obtain a separately scoped recovery decision.

## 1. Select and freeze the release commit

1. Select the exact commit intended for release and record its full SHA as
   `RELEASE_SHA` in the release evidence. Do not infer it later from a moving
   branch name.
2. Fetch the remote without modifying the worktree.
3. Verify that `HEAD`, the selected `RELEASE_SHA`, and the intended remote
   branch resolve to the same commit, and that the branch is neither ahead nor
   behind its upstream.
4. Verify `git status --short` is empty. Untracked local material is also a
   hard stop until it is classified and removed from the release worktree.
5. Verify both `git tag --list v0.1.0` and the remote tag lookup return no tag.
6. Recheck the full SHA before and after every build or approval wait. Any
   drift aborts the procedure.

## 2. Run the validation suite at the exact SHA

From a clean checkout of `RELEASE_SHA`, record tool versions and run:

```bash
git diff --check
Rscript -e 'testthat::test_dir("tests/testthat")'
python -m unittest discover -s tests -p 'test_zenodo*.py'
quarto render manuscript/smoke_test.qmd
```

Use the documented isolated Ubuntu runtime if the native R and Quarto runtimes
are incompatible. Classify all render side effects, remove only known generated
outputs, and verify the worktree is clean again. A skipped native Quarto test
is acceptable only when the isolated Quarto render passes and its environment,
command, result, side effects, and cleanup are recorded.

## 3. Build and verify the curated artifact once

Build into a new empty directory from the frozen checkout:

```bash
python scripts/zenodo/build_cohort_bundle.py --root . --output-dir RELEASE_ARTIFACT_DIR
```

Treat `fof-locomotor-capacity-cohort-0.1.0.zip` and `bundle.sha256` as immutable
release candidates. Do not rebuild between approval and publication. Record
their SHA-256 digest and preserve the exact bytes.

Verify all of the following:

- the builder reports `BUNDLE_SAFETY=PASS`;
- the ZIP contains exactly the embedded `manifest.txt` paths plus
  `SHA256SUMS`;
- every embedded checksum matches the corresponding member;
- the external `bundle.sha256` matches the ZIP bytes;
- neither the selected Git tree nor the ZIP contains local development or
  governance material outside the approved allowlist;
- the ZIP contains no protected participant data, protected analytical result,
  credential, secret, unexpected archive member, or symlink;
- `CITATION.cff`, `DESCRIPTION`, README, changelog, artifact name, and release
  notes consistently identify version `0.1.0` and the same release boundary.

## 4. Prepare release notes

Prepare notes that identify the full release SHA and ZIP SHA-256, summarize the
synthetic-only software contents, link the validation evidence, and state the
participant-data, manuscript, supplement, scientific-results, Production
Zenodo, and DOI exclusions. Do not describe the release as published before
publication succeeds.

AI-disclosure wording is non-blocking for this software release. Do not add or
silently decide disclosure text here; any manuscript, journal, or institutional
requirement remains a separate verification and decision scope.

## 5. Create the annotated tag — Owner gate

Tag signing is `NEEDS_OWNER_DECISION` before tag creation. The Owner must choose
whether the annotated tag is signed and then provide explicit **Owner tag
approval** for the exact SHA, notes, artifact digest, and signing choice.

Only after that approval, create an annotated `v0.1.0` tag targeting the full
recorded `RELEASE_SHA`. Immediately verify that dereferencing `v0.1.0^{}` yields
exactly `RELEASE_SHA`, the tag is annotated, and its message is correct. Stop
on any mismatch.

## 6. Push the tag — separate Owner gate

Present the verified local tag target and release evidence to the Owner. Only
after explicit **Owner tag-push approval**, push the single `v0.1.0` tag. Verify
the remote tag exists and dereferences to the same `RELEASE_SHA`. Do not push
other refs and do not force-push.

## 7. Draft and publish the GitHub Release — separate Owner gate

After the remote tag is verified, create a GitHub Release **draft** for
`v0.1.0`, attach the exact already-approved ZIP bytes, and use the approved
release notes. Confirm while still in draft state that the tag target, artifact
filename and digest, notes, and boundary statements match the evidence.

Present the complete draft to the Owner. Only after explicit **Owner publish
approval** may the GitHub Release be published. This approval does not
authorize any Zenodo action.

## 8. Post-release verification

After publication, independently verify and record:

- the GitHub Release is public and points to `v0.1.0`;
- the remote annotated tag dereferences to the frozen `RELEASE_SHA`;
- the downloaded ZIP matches the recorded SHA-256 and approved exact bytes;
- release notes and citation metadata identify `v0.1.0` consistently;
- no local development or governance material, participant data, protected
  result, secret, or unexpected file is exposed;
- no Production Zenodo record or DOI was created by this procedure.

Any discrepancy is an incident requiring a separately authorized response; it
must not be silently corrected by replacing assets or moving the tag.
